# Alexandria v0.2 Implementation Plan

**Goal:** Make Alexandria production-usable as a persistent, configurable agent memory server.

v0.1 proved the architecture end-to-end with 28 passing tests but stores everything in RAM and uses hardcoded defaults. v0.2 adds the features needed for daily use: persistent storage, configuration, the remaining MCP tools, and spreading activation.

**Scope principles:**

- Ship what makes the server **usable across sessions** (persistence, config, update/import tools)
- Ship what makes recall **meaningfully better** (spreading activation, cluster maintenance)
- Defer what requires external services (LLM-based extraction/consolidation, OpenAI embeddings)
- Defer what requires auth infrastructure (multi-tenancy)

---

## Key Design Decisions

| Decision | Choice | Rationale |
| ---------- | -------- | ----------- |
| Graph edges | Single `memory_edge` table with `edge_type` field | Simpler spreading activation (one table scan). Can split into per-type tables later. |
| Schema evolution | Version-tracked migrations | Future-proof. Can flatten for 1.0. Each migration is an `.surql` file with a version number. |
| Persistent storage | `surrealkv://path` via `kv-surrealkv` feature | Confirmed correct SurrealDB 3.2 syntax. Same `engine::any::connect()` API. |

## What v0.2 Includes

| # | Feature | Why now |
| --- | --------- | --------- |
| 1 | Warnings cleanup | Clean baseline before new code |
| 2 | Config file loading (`alexandria.toml`) | Needed by persistence for `data_dir` |
| 3 | Schema migration system | Persistent storage needs idempotent, versioned schema evolution |
| 4 | Persistent storage (SurrealKV on disk) | Memories must survive server restarts |
| 5 | Embedding model migration safety | Server must refuse to start if model changed without re-embed |
| 6 | Graph edges — single `memory_edge` table | Required by spreading activation and future consolidation |
| 7 | Spreading activation | Heat propagation through graph edges — core recall quality |
| 8 | `update_memory` MCP tool | Core CRUD gap — agents need to correct/refine memories |
| 9 | `import_document` MCP tool | Bulk knowledge loading is a primary use case |
| 10 | Cluster maintenance (split/merge) | Prevents cluster drift as memory count grows |

## What v0.2 Does NOT Include (v0.3+)

- Multi-tenancy (namespace/database per org/user)
- Auth & identity
- Background enrichment pipeline (LLM extract, LLM relate, consolidate)
- OpenAI embedding provider
- Cluster label generation (LLM-based)
- Full-text search (SurrealDB FTS index)
- SurrealDB native vector index (app-side cosine is fine for <100k memories)

### Task 2: Config File Loading

**What:** Load `alexandria.toml` from a standard location with env var overrides.

**Changes:**

- Add `toml` + `serde` derive dependency to `alexandria` crate
- `config.rs`: Full config struct with sections for database, embedding, heat, activation, cluster
- Load order: defaults → `~/.alexandria/config.toml` → `ALEXANDRIA_CONFIG` env path → individual env var overrides
- Print effective config on startup at INFO level

**Config struct:**

```rust
pub struct Config {
    pub data_dir: PathBuf,                    // default ~/.alexandria/data
    pub embedding_model: String,              // default all-MiniLM-L6-v2
    pub embedding_device: String,             // default cpu
    pub cluster_join_threshold: f32,          // default 0.75
    pub cluster_merge_threshold: f32,         // default 0.9
    pub cluster_cohesion_floor: f32,          // default 0.6
    pub heat_spacing_halflife: f64,           // default 86400.0
    pub activation_propagation_factor: f32,   // default 0.3
    pub activation_max_hops: u32,             // default 2
}
```

**Tests:**

- Parse a sample TOML string into Config
- Env var overrides work
- Missing file uses defaults

**Acceptance:** `alexandria.toml` is loaded and logged on startup.

### Task 3: Schema Migration System

**What:** Version-tracked schema migrations so persistent databases evolve safely.

**Changes:**

- `schema.rs` → `schema/mod.rs` with migration runner
- `schema/migrations/` directory with numbered `.surql` files
- `v001_initial.surql` — current v0.1 schema (fact, cluster, heat_state, provenance, contains_memory)
- `v002_memory_edge.surql` — new memory_edge relation table
- `v003_system_config.surql` — system_config table for embedding model tracking
- Migration runner: reads `system_config.schema_version`, runs pending migrations in order, updates version
- First boot (no `system_config` table): runs all migrations from v001

**Schema for migration tracking:**

```sql
DEFINE TABLE IF NOT EXISTS system_config SCHEMAFULL;
DEFINE FIELD key ON system_config TYPE string;
DEFINE FIELD value ON system_config TYPE string;
DEFINE FIELD updated_at ON system_config TYPE datetime DEFAULT time::now();
DEFINE INDEX idx_system_config_key ON system_config FIELDS key UNIQUE;
```

**Tests:**

- Fresh DB: all migrations run, version set to latest
- DB at v001: only v002+ run
- Re-running on up-to-date DB: no-op

**Acceptance:** Schema evolves safely across restarts.

### Task 4: Persistent Storage — SurrealKV on Disk

**What:** Switch from `mem://` to `surrealkv://path` with configurable data directory.

**Changes:**

- `connection.rs`: Add `connect_persistent(path: &str)` using `surrealkv://{path}`
- `Cargo.toml`: Add `kv-surrealkv` feature to surrealdb dependency
- `main.rs`: Use `connect_persistent(config.data_dir)` by default, fall back to `connect_embedded()` if `data_dir` is `":memory:"`
- Create `data_dir` if it doesn't exist (with `std::fs::create_dir_all`)

**Tests:**

- Existing in-memory tests unchanged (use `connect_embedded()`)
- New test: write fact → drop connection → reconnect to same path → read fact back
- Test with temp directory (cleaned up after test)

**Acceptance:** Memories persist across server restarts.

---

### Task 5: Embedding Model Migration Safety

**What:** Track which embedding model produced stored vectors. Refuse to start on mismatch.

**Changes:**

- On first boot: write `system_config { key: "embedding_model", value: model_name }` and `{ key: "embedding_dimensions", value: dims }`
- On subsequent boots: read system_config, compare against current config
- Mismatch → log error with instructions, exit with code 1
- Check happens **after** DB connect, **before** loading embedding model (fail fast)

**Tests:**

- First boot writes embedding config
- Same model on restart → boots normally
- Different model → exits with clear error

**Acceptance:** No silent embedding model mismatches.

---

### Task 6: Graph Edges — `memory_edge` Table

**What:** Single SurrealDB relation table for all semantic edges between memories.

**Schema (in `v002_memory_edge.surql`):**

```sql
DEFINE TABLE memory_edge SCHEMAFULL TYPE RELATION FROM fact TO fact;
DEFINE FIELD edge_type ON memory_edge TYPE string;
DEFINE FIELD strength ON memory_edge TYPE float DEFAULT 1.0;
DEFINE FIELD created_at ON memory_edge TYPE datetime DEFAULT time::now();
DEFINE INDEX idx_edge_type ON memory_edge FIELDS edge_type;
```

Edge types: `"relates_to"`, `"supports"`, `"contradicts"`, `"derived_from"`, `"extracted_from"`

**Repo:**

- `EdgeRepo::create_edge(from, to, edge_type, strength)` — uses `RELATE $from->memory_edge->$to`
- `EdgeRepo::get_neighbors(id, max_hops)` — multi-hop traversal via SurrealQL graph queries
- `EdgeRepo::get_edges_for(id)` — all edges incident to a memory
- Model: `MemoryEdge { id, in_node, out_node, edge_type, strength, created_at }`

**Tests:**

- Create two facts, relate them, query neighbors
- Multi-hop traversal (2 hops) returns correct results
- Edge type filtering works

**Acceptance:** Graph edges stored and queryable.

### Task 7: Spreading Activation

**What:** When a memory is accessed, propagate heat along graph edges.

**Changes:**

- `engine/heat/activation.rs`: `propagate_activation(db, edge_repo, memory_id, bump, config)`
- Walk neighbors up to `max_hops`, decay heat by `propagation_factor` per hop
- **Heat only, not stability** — second-hand activation is temporary
- Batched update in single DB round-trip
- Integrate into `store_memory` and `retrieve_memories` tools (on access)

**Tests:**

- Access A → neighbor B gets `0.3 × bump` heat
- 2-hop neighbor C gets `0.09 × bump` heat
- Neighbor stability unchanged
- No propagation beyond `max_hops`

**Acceptance:** Accessing a memory warms its graph neighbors.

---

### Task 8: `update_memory` MCP Tool

**What:** Update content/tags/confidence of an existing memory.

**Changes:**

- `tools/update.rs`: `UpdateMemoryParams { id, content?, tags?, confidence?, metadata? }`
- Content change → re-embed, update cluster assignment, create `derived_from` edge to previous version
- Tags/metadata only → update in place, no re-embed
- `MemoryRepo::update_fact(id, updates)` method

**Tests:**

- Update content → embedding changes, lineage edge created
- Update tags only → no re-embed
- Update nonexistent ID → error

**Acceptance:** Agents can refine memories with history preserved.

---

### Task 9: `import_document` MCP Tool

**What:** Bulk import a document as one or many fact records.

**Changes:**

- `engine/import/chunking.rs`: Three strategies:
  - `heading` — split on markdown `#` headers
  - `paragraph` — split on `\n\n`
  - `fixed_size` — N chars with overlap
- `tools/import.rs`: `ImportDocumentParams { content, mode, chunk_strategy?, tags?, metadata? }`
- `mode: "whole"` → single fact
- `mode: "chunk"` → multiple facts with shared `import_batch_id`, linked via `extracted_from` edges
- All chunks embedded and clustered synchronously

**Tests:**

- Whole mode: 1 fact created
- Heading chunking: 3 headings → 3 facts
- Paragraph chunking: 4 paragraphs → 4 facts
- Chunks share `import_batch_id`, linked via edges

**Acceptance:** `import_document` tool available in MCP.

---

### Task 10: Cluster Maintenance — Split & Merge

**What:** Background cluster health checks.

**Changes:**

- `engine/clusters/maintenance.rs`:
  - **Split:** When avg member-to-centroid similarity < `cohesion_floor`, split via k-means (k=2)
  - **Merge:** When two clusters' centroid similarity > `merge_threshold`, merge into one
  - `run_maintenance(db, config)` — iterate all clusters, check health
- Triggered periodically via tokio interval in `main.rs`

**Tests:**

- Diverse memories in one cluster → split into 2
- Near-identical cluster centroids → merged
- Split/merge recomputes centroids correctly

**Acceptance:** Clusters self-organize as memory grows.

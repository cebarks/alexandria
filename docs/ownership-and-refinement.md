# Operating private accounts and memory refinement

## Choose the boundary and enroll an owner

Use [explicit hosted origin, Host and CORS configuration](configuration.md#server) for HTTP. The web UI uses a browser session and CSRF protection; `/mcp` uses an account bearer token. Loopback is not authentication. For stdio, set `[auth] stdio_account` to the enrolled login in a separate stdio configuration; no HTTP origin or cookie settings are required. Keep the configuration and process under the operator's control. Hosted HTTP refuses a configured stdio identity.

With Alexandria stopped, use `alexandria bootstrap-owner --login LOGIN --password-file FILE` on a fresh persistent store. Supply the initial password in a private UTF-8 file (mode `0600` on Unix), not as a command-line argument. The command does not reset an existing password. Start HTTP, sign in at `/debug/login`, issue an agent token in Account, and configure clients with that token rather than the browser password. Tokens are displayed at issuance, not redisplayed. Administrators can create invitations, initiate recovery and suspend accounts. A signed-in owner can also issue a recovery link for their own account. Treat invitation and recovery links as credentials: distribute them privately. Recovery sets a new password and invalidates the account's existing credentials; revocation also invalidates bound live MCP authority. See `web_auth_test` and `joint_admission_test` for the covered recovery, enrollment and stream cases.

**Application admin views do not directly expose other owners' memories, session archives, review evidence or operation history.** An administrator can nevertheless issue and use a password-recovery link to reset another account's credentials and sign in as that owner. The v016 `admin_recovery_log` records issuance with the administrator, target and timestamp; it does not hide the usable link from the issuer. An already-admitted recovery request can still mint a reset link if the issuing session is revoked before the write commits. See the [deferred recovery finding](security-findings.md#deferred-in-flight-admin-recovery-issuance).

**Host administrators can read disk and backups. This is not end-to-end encryption.** Protect the data directory, backup copies, configuration, service account and provider credentials separately.

### Adopt an existing store offline

1. Stop every opener and preserve a verified, nonoverlapping backup and its receipt; see `alexandria bootstrap-owner --help` for the required backup-manifest contract. Do not open the source in the engine to probe its lock. Do not combine this operation with an embedding-model cutover.
2. Run `alexandria bootstrap-owner --login LOGIN --password-file FILE --backup-data-dir VERIFIED_BACKUP`. Use the original login and backup path to resume a partial run; `--max-rows N` bounds a migration invocation. Do not serve a required or incomplete adoption, and do not discard the backup as part of migration. Startup admission refuses until ownership migration completes.
3. The nominated owner receives the legacy records, not a shared corpus. Memories without an assigned destination enter **Unassigned**, not Personal; deleted and quarantined visibility is retained. Legacy project-targeted reminders can be held, not turned into global reminders. Review releases in **Reminder mapping**: choose Personal or an owned project for the current revision. The original target and schedule/delivery history are retained.

## Place and find memories

Personal is for account-level information; a project is an explicit owned partition. Resolve a project by sanitized origin or known selector and reuse the returned opaque handle. In HTTP, name a destination for new stores/imports; don't guess a project from a directory basename. Automatic recall sees Personal plus the one resolved current project, or Personal only when there is no known project. Explicit `assigned` is wider; asking for one invalid or foreign project does not mean “search everything.” The explicit [session archive](session-memory.md) is account-private and distinct from scoped memory recall.

The **Collections** page supports owner edits and moves. In **Classification**, review Unassigned rows, including marked quarantined rows. An MCP caller may propose a destination, not approve it. A changed proposal requires its new revision; the owner approves the displayed version for the selected rows. Scope placement and quarantine are independent: assigning a quarantined row to Personal or a project does not make it retrievable. Placement and subsequent semantic edits may stale an open quality proposal.

## Enable inference deliberately

With no routes there is no refinement inference. Operator route configuration is not consent. Set the [route and cadence keys](configuration.md#refinement), then have the owner review the effective proposer and reviewer destinations and grant consent in **Refinement → Settings**. Refinement sends selected complete focal text and bounded evidence to those endpoints; the provider may retain it under its own policy. Local endpoints are still recipients. Changing protocol, origin or gateway prefix requires new consent; restoring an old route does not revive an invalidated grant. Models are disclosed, never credentials. Changing the model or the prompt/schema changes inference-policy currency even when the egress destination is unchanged. Old proposals remain history; current automatic authority is not carried forward.

Keep **human** as the default approval mode. The first pass proposes, not applies. Secondary-LLM approval is optional, requires the operator ceiling and owner preference, and binds to the exact current candidate and policy. An inherited reviewer can use the same model and route; that is a second call, not independent judgment. Uncertain or unresolved changes are not automatically applied. Revocation/suspension can block late application even after a call was sent; they cannot recall text already delivered. A pending proposal can still be human-reviewed and applied locally after egress revocation, subject to its normal checks.

Trusted-local operators can inspect routes and grant or revoke consent for **only** the configured account using `alexandria refinement`; these commands do not invoke a model. The separate explicit offline `dream --job refine` runs one bounded assigned-scope turn for that administrator's own workspace, with consent. Bare `dream` and `--job all` are model-free housekeeping, not refinement. Do not point offline commands at a running store.

## Review, apply and revert

Open **Refinement** for the account-private queue and detail: inspect originals, proposed changes, rationale, uncertainties and model-policy status before approving, dismissing or deferring the displayed revision. The six categories are rewrite, duplicate/consolidation, contradiction, noise/quarantine, supersession and split. Quality approval is individual and revision-specific. Existing originals are retained, not hard-deleted. Opening a queue or detail page does not invoke a model. Deferred proposals are excluded by default and remain available in the **Deferred** filter. With current consent, the owner can queue an assigned assessment, assess a single identified Unassigned memory, or request an opinion or regeneration on a proposal. Submission links to an owner-only attempt status. These browser submissions are not MCP tools, and the assigned-scope offline CLI is not an Unassigned submission path.

Unassigned is never scheduled, never searched in ordinary recall and never authorized for automatic application. A supported human-approved cleanup leaves the result Unassigned; classification remains a separate owner action. Evidence selection cannot silently widen into assigned projects. **Refinement does not assess contradictions between Personal and a project**, even when recall reads both. It also does not cross project or account boundaries.

Use **Operations** or the links from a refinement detail to inspect the owner's private operation history and before/after state. Rollback is conditional: current semantic effects and incident references must still match the recorded postimage. If someone moved, edited or linked a source in the meantime, inspect the intervening operation rather than forcing a revert. Access/heat changes alone do not invalidate rollback, and later heat is not rewound. For derived cluster bookkeeping alone, the same request may prepare at most three times with current authority, reloading derived state without changing approved effects. A changed source, evidence or named membership effect is stale, not a bookkeeping retry. Exhaustion does not preserve reusable automatic approval.

## Run and qualify

Five housekeeping jobs retain their own schedules; four emit maintenance audits. `sweep` updates heat only and is not audited. Refinement uses its own enqueue cadence and a separate serialized worker with durable, fair progress and bounded request/queue/rolling-attempt budgets. These caps constrain work, not latency or a provider invoice; a call already sent may still be billable. The administrator's Maintenance view shows aggregate housekeeping counts, not private refinements, egress evidence or operation snapshots.

`just refinement-eval` scores checked-in deterministic proposals against human-reviewed labels; it runs no model and does not establish provider quality. The compiled fixture and hermetic tests use disposable data, not production configuration or credentials. Hosted prompt-path latency/throughput, live model quality, and a native browser exercise are separate from hermetic admission; do not infer those results from the fixture. See [the evaluator guide](../tools/refinement-evaluation/README.md) for its scope and limitations.
